# Device evidence trust and activation boundary

This release does not enroll devices or enable protocol 2. Owner JWTs and device-topic membership cannot enroll, replace or revoke a trusted key. All new tables and functions start closed to every API role.

Before activating a device, the release operator must use an authenticated administrative channel to that exact original device, provision an Ed25519 key in its encrypted native secret store, and obtain its public SPKI and key ID through that channel. Compare the public fingerprint at both endpoints through an independently authenticated pairing/deployment path. A public key learned from an owner broadcast, an editable device row or the response under verification is never trusted. Record the audited enrollment reference with owner, device and public key in `identity.connection_device_evidence_keys`. Never export the private key, print encrypted secrets or place them in this repository. There is deliberately no owner-facing auto-enrollment endpoint.

An existing active key cannot be silently replaced: the partial unique index permits one active key per owner/device. Rotation requires quiescing the affected device, fencing or resolving its original attempts, independently verifying the replacement and retaining the revoked enrollment for audit. Loss of the key or unreachable native storage requires an operator-owned incident and a proven original custody fence; a cloud epoch change alone does not fence an offline SQLite writer. That device remains activation-blocked until this is resolved. No finite automatic completion time is claimed for a device for which a real fence cannot be obtained.

The verifier issues a fresh 60-second challenge from the trusted registry and binds it to owner/device/original UUID/attempt/action. The actual native journal read/fence signs the complete response. The real requester and the privileged submission adapter both verify Ed25519 against the independently read registry key. In the outcome transaction the database rechecks the same active key and device ownership, exact challenge/context, expiration and durable single-consumption identity. Repeated delivery can only return the already-settled original outcome; no challenge can justify another attempt or a different observation. API roles cannot call the internal acceptance helpers. The original ACK and deletion transaction remain unchanged.

Rollback first quiesces new actions and stops verification schedulers, then closes new writer grants. Keep trusted enrollments, challenges, original proofs and independent results. Never replay effects or restore revoked credentials. A resumed verifier needs the matching signed native adapter and a renewed activation review.
