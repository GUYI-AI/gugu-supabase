# Application-owner baseline in CI

`release/production-object-owners.json` contains only object names and owner names. The read-only query in `scripts/ci/application-owner-catalog.sql` captures application relations (tables, views, materialized views, partitions and sequences), routines with exact overload identities, schemas and the database-owner alias binding. Platform schemas and extension members are explicitly excluded in that query. A trigger follows its target relation's owner.

Rather than infer incomplete PL/pgSQL call graphs, CI checks the stronger existing ownership invariant across this entire application inventory and the freshly installed candidate. Thus existing migration targets and application runtime-write tables cannot borrow a non-postgres owner exception. Objects newly created by pending migrations must also pass the live fixture check. This is an owner check, not proof of object existence, migration ordering, ACLs, runtime authorization or platform-write capabilities; those checks remain separate.

Production snapshots require postgres. The standard public/pg_database_owner alias additionally requires the actual database owner to be postgres. Only an owned disposable fixture may use the exact alternative pair public=pg_database_owner/database=supabase_admin. No generic role, NOLOGIN pattern or application-owner exception is accepted.

PR CI obtains the checker, query and production snapshot from the PR's trusted base commit. A feature PR cannot edit its own captured facts into a green baseline. Candidate snapshot changes are also linted, and installation is checked with the trusted checker. The initial bootstrap explicitly reports that base enforcement is not installed yet; it runs the candidate tests and requires review. Once the target branch has the guard, stale bootstrap events are refused until synchronized.

After every database deployment or privileged owner repair, an operator captures the full catalog through the existing approved read-only route with a short statement/transaction deadline, then opens a normal snapshot refresh PR. CI never connects to production and holds no production credentials. Snapshot files keep the two-field records only; capture time, query digest, source provenance and review belong in the maintenance description. A snapshot is point-in-time evidence; the live deployment owner gate still runs before/after migrations.

The complete distribution inventory stays private. To refresh the public file, intersect it with catalog names from a community-only disposable installation via `--filter-production <private-json> --fixture-root <owned-checkout> --output <new-public-json>`. The filter first rejects violations in the full private inventory, then emits only names present in the community installation, with production owner facts. Never copy a private inventory into the public repository. This baseline was captured on 2026-11-15; 798 published records match community names.

On failure, use the reviewed privileged repair/CD process before deployment, then refresh the read-only snapshot. Do not rename owners in JSON, broaden the platform list or reset a database to make CI green.
