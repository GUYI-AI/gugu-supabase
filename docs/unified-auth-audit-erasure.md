# Account deletion with registered audit processing

Refs #265, #291 and #302. The Auth request commits account deletion together with a restricted redaction registration; it does not scan the Auth or file-action audits. The registration/context release `100400` and batch helpers `100500` precede the unified caller/worker `101000`, after the independent file `090000` and Auth `100000` releases. Platform time-index preparation remains in the separately reviewed normal release path. No installed migration is changed.

The caller preserves the existing erasure body, ordered locks and DML using exact predecessor anchors. The Auth trigger passes trusted `OLD.id` and `OLD.email`; missing or changed lifecycle identity sets are refused. A registration failure or a later core-erasure failure rolls back Auth and the registration together. The old private one-argument signature remains compatible with NULL email, and API roles cannot call either erasure capability or any worker capability.

Background processing claims a locked registered job, creates an exact transaction/PID/lease context and scans at most 1000 candidate rows per batch. Helpers check the live context at both ends. A skipped row preserves the page cursor; an empty or drained page never proves completion. The worker commits bounded batches independently. A failed batch retains its criteria and retry position; the driver commits that recovery state before visibly failing its cron run. An asynchronous failure does not restore an already-deleted account.

Round one targets 24 hours and writes only a `redacted` proof after actual Auth and file residual counts are zero. The restricted criteria stay for a second scan on day seven. Only another real zero result writes `closed` and removes the criteria. A nonzero second result requires manual review. Daily checks inspect actual logs, including jobs waiting for the second scan; the separate guard fails when verification is missing, incomplete, overdue or has residuals/manual work. Alert routing and delivery still require deployment acceptance. The internal 15-calendar-day escalation is a conservative earlier bound, not a claim to interpret the approved 15-working-day maximum.

Nightly processing is selected by the Shanghai hour inside an hourly trigger, independently of the scheduler timezone; retries/catch-up run every ten minutes. The procedure is SECURITY INVOKER with no function SET clause so its trusted caller can commit each batch. Scheduled procedure commands contain only `CALL`, since wrapping it in a multi-command implicit transaction would prevent transaction control. The elapsed-time budget is soft between batches, not a promised SQL statement deadline. Daily check/guard commands have a separate 30-second statement timeout. API roles cannot invoke the procedure.

Redaction is limited to registered identities and their approved fields. Explicit new actor/target IDs protect a replacement account even if the email is reused; the scopes remain independent and provider UUIDs remain security evidence. No global email-only redaction or long-lived email-fingerprint registry is introduced. The bounded two-scan policy explicitly accepts rare later records. A success page must not claim all records have been deleted. Pending audit data stays restricted to its existing small set of readers and is not used for analytics or identification.

The real Auth HTTP suite covers registration/core rollback, asynchronous retry without account restoration, retained criteria and two proofs, NULL/empty email, a replacement account, skip-locked pages, manual review, a real committable procedure failure and actual daily residual alerts. Synthetic audit-scale cases record HTTP deletion latency separately from processing; they do not reproduce every production message/command relationship or prove the production latency gate.

The independent 180-day audit-retention task remains unchanged. Other production gates remain open: non-FK/financial cleanup, local/source-session cleanup, real confirmation-mail receipt, alert delivery and the measured account-deletion latency target. The earlier 4.616-second Auth measurement predates these audit scans; moving them off the request cannot by itself prove that the earlier bottleneck is fixed.
